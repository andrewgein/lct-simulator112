# Review Service

Сервис формирует результаты проверки прохождения уровня для операторов системы 112 и операторов ДДС.

## Архитектура

```text
com/simulator112/review_service
├── domain
│   ├── model
│   └── evaluation
├── application
│   ├── port/in
│   ├── port/out
│   └── service
└── adapter
    ├── in
    │   ├── grpc
    │   └── rest
    ├── out/persistence
    └── config
```

Application-слой работает только с domain/application-моделями и портами. Protobuf преобразуется в gRPC-адаптере, JPA находится только в persistence-адаптере.

Оценивание построено как расширяемый доменный pipeline:

```text
ReviewRubric
└── Rubric
    └── Stage
        └── Criterion
```

`RubricBuilder` проверяет, что сумма максимальных баллов критериев одного инцидента равна 100. SYSTEM_112 и DDS используют собственные наборы этапов и критериев.

## Проверка SYSTEM_112

На каждый инцидент выделяется 100 баллов:

- поля карточек — 70;
- операции создания и простые связи карточек — 20;
- обработка всех звонков — 10.

Карточки собираются из упорядоченных ревизий. Ожидаемые поля формируются из снимка сценария: данные заявителя берутся из звонка, а количество пострадавших и классификаторы — из этапа. `PreparedCardTemplate` в проверке SYSTEM_112 не используется.

## Проверка DDS

На каждый инцидент выделяется 100 баллов:

- успешное выполнение активированных этапов — 80;
- успешный терминальный результат инцидента — 20.

Context-service передаёт runtime-прогресс уровня, включая результаты всех DDS-этапов.

## Подробный отчёт и жизненный цикл

Context-service передаёт этапы и звонки сценария, критерии, transcript, время начала/отправки, timestamps ревизий карточек и DDS-этапов. Review-service формирует:

- автоматический и итоговый баллы;
- длительность, норматив (30 секунд на инцидент) и превышение;
- атомарные `CriterionResult` для отдельных полей, операций, звонков и DDS-этапов; бюджет каждого критерия распределяется между его проверками;
- безопасный `feedback`, который указывает место ошибки, но не раскрывает эталонные значения и формулировки критериев оценки диалога;
- результаты критериев оценки диалога, заданных преподавателем.

Отдельная сущность для замечаний не используется: причины начисления и снятия баллов хранятся непосредственно в `criterion_results.feedback`.

После автоматической проверки результат и учебный контекст сразу получают статус `DONE`; подтверждение преподавателя не требуется. Пользователь с ролью `SUPERVISOR` может позднее скорректировать итоговый балл и оставить комментарий. Автоматический балл при этом сохраняется отдельно для аудита.

Для заданий SYSTEM_112 преподаватель может задавать критерии оценки диалога и вес каждого критерия. Их суммарный бюджет ограничен 40 баллами; оставшиеся баллы автоматически перераспределяются между основными рубриками с сохранением пропорций. В заданиях ДДС критерии диалога не используются. Семантическая проверка выполняется моделью `cointegrated/rubert-tiny-bilingual-nli` через MLServer: каждая реплика оператора сопоставляется с гипотезой критерия, а критерию назначается максимальная вероятность `entailment`.

Конфигурация модели находится в `mlserver/rubert-tiny-bilingual-nli/model-settings.json`. Подключение настраивается переменными окружения:

- `MLSERVER_URL` — адрес MLServer, по умолчанию `http://localhost:8080`;
- `MLSERVER_MODEL_NAME` — имя модели, по умолчанию `rubert-tiny-bilingual-nli`;
- `MLSERVER_ENTAILMENT_THRESHOLD` — порог выполнения критерия, по умолчанию `0.8`.

Каждая пара «реплика оператора — гипотеза критерия» проверяется отдельным запросом, после чего для критерия выбирается максимальная вероятность.

## API

- gRPC `sendOnReview` — принять завершённый контекст;
- gRPC `getReview` — получить статус проверки;
- `GET /api/v1/review` — проверки пользователя;
- `GET /api/v1/review/{contextId}` — подробный результат проверки контекста;
- `POST /api/v1/review/{contextId}/confirm` — необязательная экспертная корректировка (`SUPERVISOR`), тело: `{ "finalScore": 90, "comment": "..." }`.

## Хранение

Используется нормализованная PostgreSQL-схема без JSONB. Flyway history переписана в единую `V1`; существующую локальную БД review-service необходимо пересоздать.
